# Engineering Decisions

This document records important technical decisions made during the development of the platform and the reasoning behind them.

The goal is not only to document what was deployed, but to explain why the platform evolved in its current direction.

---

## 1. Docker Compose Before Kubernetes

### Decision

Docker Compose was used before Kubernetes.

### Reason

The initial objective was to establish a working containerized application stack consisting of the Employee API and PostgreSQL.

Docker Compose provided a simple way to:

* Build the application image
* Run multiple containers
* Create application networking
* Configure environment variables
* Test API-to-database communication

### Why We Later Moved to Kubernetes

As the project became a platform-engineering project rather than only a local application, additional capabilities became important:

* Workload orchestration
* Replica management
* Service discovery
* Persistent storage
* Secrets management
* Scheduling
* Scaling
* Networking
* Observability

This created the architectural transition:

```text
Docker Compose
      ↓
Kubernetes
```

---

## 2. Kubernetes Deployment for the Employee API

### Decision

The Employee API is managed using a Kubernetes Deployment.

### Configuration

```text
replicas: 2
```

### Reason

The API is a stateless application layer and can therefore be replicated.

Two replicas allow Kubernetes to maintain another API instance if one Pod becomes unavailable.

The replicas currently run across two worker nodes:

```text
platform-cluster-worker
└── Employee API Pod

platform-cluster-worker2
└── Employee API Pod
```

This provides application-layer redundancy.

---

## 3. StatefulSet for PostgreSQL

### Decision

PostgreSQL is managed using a Kubernetes StatefulSet rather than a Deployment.

### Reason

PostgreSQL is a stateful workload.

A StatefulSet provides stable identity and is designed for workloads that require persistent storage and predictable Pod identity.

The current configuration is:

```text
StatefulSet: employee-db
Replicas: 1
Pod: employee-db-0
```

---

## 4. One PostgreSQL Replica

### Decision

PostgreSQL currently runs with one replica.

### Reason

The current environment is a development/learning platform rather than a production database cluster.

Running a single PostgreSQL instance keeps the architecture simple while allowing us to focus on:

* Persistent storage
* Database connectivity
* Kubernetes networking
* Secrets management
* Application integration

### Current Limitation

A single PostgreSQL Pod is **not highly available**.

Persistent storage protects database data from simple Pod/container recreation, but it does not provide database-level failover.

Therefore:

```text
API Availability
      ↓
2 replicas
      ↓
Redundant application layer


Database Availability
      ↓
1 PostgreSQL replica
      ↓
No database-level failover yet
```

A future production-oriented iteration can introduce PostgreSQL replication, a highly available PostgreSQL operator, or a managed database service.

---

## 5. Persistent Storage for PostgreSQL

### Decision

PostgreSQL uses a PersistentVolumeClaim generated by the StatefulSet.

### Current configuration

```text
Storage request: 1Gi
Access mode: ReadWriteOnce
StorageClass: standard
```

The current PVC is:

```text
postgres-data-employee-db-0
```

### Reason

Database data should not depend on the lifetime of the PostgreSQL container filesystem.

The storage lifecycle is therefore separated from the Pod lifecycle.

```text
PostgreSQL Pod
      ↓
PersistentVolumeClaim
      ↓
PersistentVolume
```

This means recreating the PostgreSQL Pod does not automatically mean losing the database data.

---

## 6. ClusterIP for Internal Application Communication

### Decision

The Employee API was initially exposed using a ClusterIP Service.

### Reason

The API first needed to be reachable from other workloads inside the Kubernetes cluster.

ClusterIP provides:

* Stable virtual IP
* Stable DNS name
* Load balancing across API replicas
* No unnecessary external exposure

Internal clients can use:

```text
http://employee-api:5000
```

This was verified using a temporary curl Pod.

---

## 7. NodePort for External Testing

### Decision

The Employee API was later exposed using a NodePort.

### Reason

NodePort provides a simple way to demonstrate external access to a Kubernetes Service without introducing an Ingress Controller yet.

The current NodePort is:

```text
30445
```

External testing successfully reached:

```text
http://172.20.0.2:30445/
```

### Why NodePort Is Not the Final Architecture

NodePort is useful for learning and intermediate testing, but it is not the intended final application entry point.

The next networking stage is Ingress.

---

## 8. Kubernetes DNS Instead of Pod IPs

### Decision

Applications communicate with PostgreSQL using the Service name:

```text
employee-db
```

rather than the PostgreSQL Pod IP.

### Reason

Pod IP addresses are ephemeral.

Kubernetes Services provide a stable network abstraction.

The Employee API therefore uses:

```text
DB_HOST=employee-db
```

instead of something like:

```text
DB_HOST=10.244.x.x
```

This allows PostgreSQL Pods to be recreated without requiring the application configuration to change.

---

## 9. Vault and Kubernetes Secrets

### Decision

Database credentials are managed through HashiCorp Vault and exposed to the application through a Kubernetes Secret.

### Architecture

```text
HashiCorp Vault
      ↓
Vault Secrets Operator
      ↓
Kubernetes Secret
      ↓
Employee API
```

### Reason

Database credentials should not be hardcoded into:

* Application source code
* Docker images
* Kubernetes manifests
* Git repositories

The Employee API receives the database password through:

```text
DB_PASSWORD
```

from:

```text
employee-db-secret
```

---

## 10. Versioned Container Images

### Decision

The Kubernetes Deployment uses:

```text
ghcr.io/abiamahladi/employee-api:v2
```

instead of:

```text
ghcr.io/abiamahladi/employee-api:latest
```

### Reason

The `latest` tag is mutable.

A versioned image provides a clear relationship between:

```text
Source Code
    ↓
Docker Build
    ↓
employee-api:v2
    ↓
GHCR
    ↓
Kubernetes Deployment
```

This improves deployment reproducibility and makes rollback easier.

---

## 11. GHCR as the Container Registry

### Decision

GitHub Container Registry is being used to store the Employee API container image.

Current image:

```text
ghcr.io/abiamahladi/employee-api:v2
```

### Reason

GHCR integrates naturally with the GitHub-based development workflow.

It provides a central location from which Kubernetes nodes can retrieve application images.

## 12. Gunicorn for the Application Container

### Decision

Gunicorn is used to serve the Flask application inside the container.

### Reason

Flask's built-in development server is intended for development and debugging rather than production-style application serving.

Gunicorn provides a production-oriented WSGI server for the Flask application.

The Kubernetes container therefore runs the application through Gunicorn rather than relying on:

```python
app.run(...)
```

### Important Debugging Lesson

The use of Gunicorn exposed an application initialization issue.

The original database connection was initialized under:

```python
if __name__ == "__main__":
```

When running:

```text
python app.py
```

that block executes.

However, when Gunicorn imports:

```text
app
```

that block does not execute.

This caused the application to depend incorrectly on initialization code that only ran when the file was executed directly.

The application was subsequently refactored so database connections are created through the application's database connection function rather than relying on the `__main__` execution path.

### Engineering Lesson

Application startup behavior must be understood in relation to the process used to serve the application.

---

## 13. Debugging Methodology

When `/health` initially returned HTTP 500, the investigation followed the communication path rather than immediately changing configuration.

The investigation checked:

1. Application logs
2. Database environment variables
3. Kubernetes DNS
4. Network connectivity
5. PostgreSQL authentication
6. Application database connection initialization

The root cause was identified as an application connection initialization problem rather than a Kubernetes networking problem.

This demonstrated the importance of isolating each layer before changing configuration.

---

## 14. Two API Replicas, One Database

The current architecture deliberately has different scaling characteristics:

```text
Employee API
    ↓
2 replicas

PostgreSQL
    ↓
1 replica
```

This reflects the difference between stateless and stateful workloads.

The API can scale horizontally because requests can be handled by multiple equivalent instances.

The database requires state management and cannot simply be duplicated without considering data consistency, replication, failover, and storage.

This distinction will become increasingly important as the platform moves toward production engineering.

## 15. Vault Before PostgreSQL (Dependency Ordering)

### Decision

During a full platform rebuild, Vault and the Vault Secrets Operator were deployed and configured **before** PostgreSQL, rather than after.

### Reason

The PostgreSQL manifest consumes its database password from a Kubernetes Secret (`employee-db-secret`) that is created by the Vault Secrets Operator, not defined directly in the manifest.

```text
Vault
  ↓
Vault Secrets Operator
  ↓
employee-db-secret (synced from Vault)
  ↓
PostgreSQL
```

Deploying PostgreSQL before this chain exists causes the Pod to fail on startup, since the referenced Secret does not yet exist.

### Engineering Lesson

Dependency order matters as much as the individual manifests. Before rebuilding any part of the platform, existing CRs and manifests should be reviewed to identify what a component actually depends on, rather than assuming the original build order.

## 16. Argo CD for GitOps

### Decision

Argo CD was introduced to continuously reconcile the cluster state with the `kubernetes/` directory in this repository.

### Configuration

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

### Reason

Prior stages relied on manually running `kubectl apply` against manifests. This works, but does not protect against configuration drift — a manual `kubectl edit` or `kubectl scale` against a live resource would silently diverge from what is declared in Git.

`selfHeal: true` closes this gap: any live-state drift, from any source, is automatically reverted back to match Git. `prune: true` ensures resources removed from Git are also removed from the cluster.

### Verification

Drift correction was tested directly by manually scaling the Employee API Deployment to 0 replicas outside of Git:

```text
kubectl scale deployment employee-api --replicas=0
```

Argo CD detected the drift and recreated the Pods to match the Git-declared replica count within seconds, confirming the self-healing loop works end-to-end.

## 17. Cluster-Wide Default StorageClass

### Decision

The `local-path` StorageClass was set as the cluster-wide default.

```text
kubectl patch storageclass local-path -p \
  '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

### Reason

Helm charts (Prometheus, Alertmanager) create PersistentVolumeClaims without specifying a StorageClass explicitly, relying on a cluster default to exist. Without one, PVCs remained in a `Pending` state indefinitely, and dependent Pods could not be scheduled.

Since `local-path` is the only StorageClass available in this cluster, marking it default avoids needing to pass an explicit `storageClass` override to every future Helm install.

---

## 18. Prometheus and Grafana via Separate Helm Charts

### Decision

Prometheus and Grafana were installed as two independent Helm releases (`prometheus-community/prometheus` and `grafana/grafana`) into a dedicated `monitoring` namespace, rather than using a single bundled stack (e.g. `kube-prometheus-stack`).

### Reason

Installing each component separately provides clearer visibility into how each piece is configured and connected, which better serves the learning objective of this project.

### Architecture

```text
Kubernetes cluster
  ↓ (scrape)
Prometheus (server, node-exporter, kube-state-metrics, Alertmanager)
  ↓ (PromQL query, via Grafana data source)
Grafana
  ↓
Dashboards
```

Grafana was connected to Prometheus as a data source over the in-cluster service DNS name (`prometheus-server.monitoring.svc.cluster.local`), and a community Kubernetes cluster monitoring dashboard was imported to visualize node, pod, and cluster-level metrics.

### Persistence

Grafana's Helm chart disables persistent storage by default. This was explicitly enabled (`persistence.enabled=true`) so dashboards and configuration survive Pod restarts, using the same `local-path` StorageClass.
